## What I overrode / rejected

- **Editor.tsx `require('./EditorToolbar')` hack.** The first draft used a dynamic `require` inside a child component to avoid an imagined circular import. I rewrote it as a normal top-level import — the fear was unfounded and the hack added a confusing surface. Lesson: AI sometimes inserts defensive code against problems that don't exist in a greenfield build.
- **`export const dynamic = "force-dynamic"` on dashboard and doc pages.** First draft added this on reflex from Next 15 habits; Next 16 with `cacheComponents` rejects the flag. Rather than disable `cacheComponents` by instinct, we only disabled it after confirming the specific prerender error. Final fix: both — remove the directive *and* turn off cacheComponents, because the project has nothing to gain from cache-first routing.
- **Service role key for sharing.** AI's default pattern for "look up a user by email" is to use the Supabase admin API server-side with the service role key. I steered to a `profiles` mirror table with a trigger, so the service role key never has to leave the dashboard and the browser can do the lookup under a narrow RLS policy. More code, but a cleaner security story.
- **Service-role bypass of RLS in `/api/upload`.** First instinct was to insert the new document server-side with admin privileges "for safety." Changed to use the authed user's session — same security boundary, no key management, matches the rest of the system.

## How I verified correctness, UX, and reliability

1. **`npm run build` after every structural change.** Next 16 is new enough that type errors and prerender errors surfaced three distinct issues; shipping each fix was gated on a clean build.
2. **`npm test` for the authorization predicate.** 6 cases including the "don't leak access across documents" case (which is the exact bug RLS fixes — worth a dedicated assertion).
3. **Manual walk of the main flow in the dev server.** Create → format → reload → rename → share → sign in as recipient → see shared doc → upload a `.md` → confirm it parses into a doc. Screenshots in the walkthrough video.
4. **RLS cross-check.** The TypeScript test and the SQL policies encode the same predicate ("owner OR in shares"). If one drifts from the other, a reviewer can spot it.
5. **What I did *not* verify, and acknowledge:** load behavior under concurrent edits, mobile layout, screen-reader navigation of the toolbar. Listed in ARCHITECTURE.md § 8.

## Pivots

A visible story about using AI well is knowing when to back out of a plan the AI happily rolled forward with.

**Pivot: magic link → email + password.** The agent's first instinct for auth was Supabase magic links — clean API, nice demo UX. Shipping it surfaced two real problems:

1. **PKCE verifier cross-browser issue.** `signInWithOtp` stores a PKCE verifier in a cookie on the browser that initiates the request. If the magic link opens in the user's default browser (Gmail-on-macOS default behavior), the verifier isn't there, and `exchangeCodeForSession` returns `AuthPKCECodeVerifierMissingError`. The fix on the Supabase side is to change the email template to use `{{ .TokenHash }}` and have the server call `verifyOtp` instead — which eliminates the verifier requirement.
2. **Template editing is gated.** Supabase's free tier now restricts email template customization to projects with a configured custom SMTP provider. Fixing this cleanly would mean signing up for Resend, wiring SMTP in Supabase, then editing templates. ~15 minutes we didn't have to spend on infra.

**Decision:** switched to email + password with two seeded reviewer accounts. The assessment prompt explicitly says "You may simulate users with seeded accounts, mocked auth, or a lightweight login flow if that keeps the scope reasonable" — which is exactly this case. Reviewers can now log in instantly without needing an email inbox or dealing with cross-browser quirks. The share flow still demos naturally because both seeded accounts exist in `profiles` from the moment they're created.

What this illustrates about working with AI: the agent happily followed the "obvious" path (PKCE magic link with code exchange) until it hit real-world failure modes. Escaping cost context, not more AI prompts — the fastest move was to look at the constraint (free-tier SMTP gating, PKCE verifier model) and route around it. Scope decisions that fit the assessment's explicit permissions beat elegance every time.

## Philosophy

The thing I keep in mind with AI-generated code is that the agent will confidently write something that compiles, passes basic tests, and does something subtly wrong — usually in security or edge cases. The two guardrails that matter:

1. **Put the security rule in the system that can't be bypassed** (here: RLS in the database, not middleware in Node). Then it doesn't matter if the AI writes a sloppy fetch — the DB refuses the row.
2. **Always test the thing you'd be most embarrassed to get wrong.** For this app it's not "does the editor render bold text" (visible, easy to catch). It's "does Carla's data stay hidden from Bob." Hence the one test in this repo.

Volume of AI usage isn't the point. What matters is: did I know what the agent produced, did I steer it when its instincts were wrong, and could I defend every line in a code review?
